# Axb Predictive-Echo Control

## Overview

Implements the Axb*1c/d predictive-echo control loop for Optimus-class humanoids. The robot never builds a full spatial map. Its only environmental belief is an internal EchoHypothesis of scatterers, updated exclusively from real acoustic returns after action. All decisions are made against a predicted echo generated by a Sandbox simulation of that hypothesis.

Core cycle:

```
predict echo → decide → PUSH path → do → hear real echo → correct → repeat
```

## Core Invariants (never violate)

1. **No world mapping.** Environment state is only ground-station variables + a ground-plane scan. The robot never receives obstacle positions directly.
2. **d is always from the predicted echo**, never from the real return. Real echo is used only for hypothesis correction and surprise measurement.
3. **Path is always pushed** to the ground station before the robot moves.
4. Solve equation is fixed form: `x = pinv(A) @ b * (1.0 / c) / d`

## Key Classes

- `GroundStation` — holds variables (goal, ground_ok). Obstacles exist only as ground truth for the Ears simulator; the robot never sees them.
- `EchoHypothesis` — robot's internal scatterer list. Methods: `predict(pose)`, `correct(pose, real_echoes)`, `surprise(pose, real_echoes)`.
- `Sandbox` — deep-copies robot state + hypothesis, simulates an action, returns the *predicted* echo and the risk divisor `d`.
- `AxbController` — samples trial directions, runs each through Sandbox, scores by goal progress minus predicted risk, returns best `x`.
- `Ears` — produces real time-of-flight returns (sim or hardware transducer).

## Risk Divisor

```python
nearest = predicted[0]["range_m"] if predicted else np.inf
d = 1.0 + max(0.0, 1.0 - nearest / 2.0)   # 1.0 (safe) … 2.0 (close)
```

Higher `d` shrinks the step size.

## Usage

When the user asks to run, extend, adapt, or reason about this loop:

1. Load and (if needed) execute `scripts/axb_predictive_echo.py`.
2. Preserve the predict → decide → push → do → hear → correct order.
3. Keep all spatial belief inside `EchoHypothesis`; never inject external maps.
4. For hardware, replace `Ears.listen` with real transducer + mic pipeline; the rest of the architecture stays identical.
5. For multi-step or 3-D extensions, keep the same solve form and predicted-echo risk source.

## Extension Points

- Change `n_guesses` or noise scale in `AxbController` for exploration vs exploitation.
- Add more sophisticated scatterer models inside `EchoHypothesis.correct`.
- Wire real audio hardware into `Ears`.
- Surface additional ground-station variables that the ground scan can consume, but never pass obstacle geometry to the robot.

## Robot Embodiment

The full Optimus-class robot is provided as `AxbRobot`:

```python
from scripts.axb_robot import AxbRobot, GroundStation

station = GroundStation(goal=[4.0, 0.0])
robot = AxbRobot(station, name="Axb-Optimus-01")

# single cycle
status = robot.step()

# or run until goal / max steps
final = robot.run(max_steps=20)
print(robot)          # <AxbRobot 'Axb-Optimus-01' pose=... status='reached demand point'>
```

`AxbRobot` owns the hypothesis, controller, ears, and pose. It strictly preserves the predict → decide → push → do → hear → correct order and never receives obstacle geometry.

### Wait-and-See Mode

The robot can wait for any topic and report what it sees in text, applying the same predictive-echo cycle to language:

```python
print(robot.wait_and_see("any topic here"))
```

Or enter continuous interactive mode:

```bash
python scripts/axb_robot.py --wait
```

In wait-and-see the robot pings the topic, forms a predicted range, receives a return, measures surprise, and reports its corrected internal view. It still holds no external map — only the hypothesis formed from the return.

**Surprise drives questions.** After the cycle the robot generates follow-up questions whose number and depth scale with the surprise score:
- low surprise → light confirmation questions
- medium surprise → clarifying questions
- high surprise → strong probing questions

The surprise score is the driver that decides what the robot asks next.

**Release & Drag.** After the first echo the robot can count its responses, search the topic, and drag external signal into a fuller response while still obeying the core invariants. This turns a single ping into an accumulating conversation.
